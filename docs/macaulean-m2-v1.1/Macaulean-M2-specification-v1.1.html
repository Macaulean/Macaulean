1. Lexical structure

Source: lex.d, ctype.d, parser.d (literal conversion), binding.d (operator words).

1.1 Source text

Source text is a sequence of bytes. It is conventionally UTF-8, but the lexer works on bytes. The only multibyte-aware rule is the one for mathematical-operator characters (§1.6). A source unit is one of: a file, the standard input (interactive or not), or a string passed to value, which is lexed as if a newline were appended.

1.2 Character classes

class members
letter A–Z, a–z, and every byte 0x80–0xFF
digit 0–9
alnum letter ∪ digit ∪ { $, ' }
white space (0x20), tab (0x09), carriage return (0x0D)
newline line feed (0x0A)
quote "

Newline is not white space. It is a token (§1.10).

1.3 Comments and white space

Before each token the lexer repeatedly skips:

  • white characters;
  • line comments: -- up to, but not including, the next newline (or end of input);
  • block comments: -* … *-. They do not nest: the first *- ends the comment. An unterminated block comment is a lexical error ("EOF in block comment -* ... *- beginning here");
  • a shebang line: if #! occurs at line 1, column 0, the rest of that line.

Note that -* always starts a comment, so a -*b is a followed by a comment.

1.4 Tokens and first-registration-wins word history

A token carries its raw spelling/source slice, lexical category, byte position, and followsNewline flag. The flag records newline tokens skipped by the cursor, not an approximation based on whether arbitrary preceding comments contain line feeds. Identifier/operator tokens have lexical type id; integer, real, and string literals are separate occurrence categories.

Identifier/operator words are registered by exact byte spelling. First registration wins:

internWord(key, requestedProfile):
    if key is already registered:
        return its existing immutable profile; do not overwrite it
    otherwise:
        record (key, requestedProfile); return that record

Register the built-in vocabulary before user input. Ordinary names and generic mathematical-operator words request GenericProfile; previously registered keywords retain their special profile. Record ordinary names too: a word already seen as generic must not acquire new parse behavior through a later dictionary alias. Numeric/string literal occurrences need not be interned.

A quoted symbol's canonical word, a dictionary entry's lookup spelling, and an occurrence's frozen lexical profile remain separate. Aliasing a dictionary name can request a copied profile, but cannot overwrite prior registration or add punctuation-trie paths (§3.8). A cached lookahead token retains the profile it had when read.

Source spelling and M2 strings are bytes, not Unicode-normalized strings. A valid-UTF-8 Lean String interface is only an adapter. Literal tokens retain source spelling; real constants are decoded during lowering at the then-current default precision (§4.2). Artificial EOF/EOC/NEWLINE tokens cannot be created by typing their diagnostic names.

This integrates the v1.0 R1/R2/R10 decisions; the archived supplied reference's blanket statement that all word occurrences are interned is not retained.

1.5 Token recognition order

After skipping white space and comments, the lexer examines the next character(s) and applies the first matching rule:

  1. end of input → EOF token;
  2. newline → NEWLINE token (or end-of-cell in "full-lines" input mode, used by front ends such as TeXmacs);
  3. the next two bytes begin a mathematical-operator character (§1.6) → a math-operator token;
  4. a letter → an identifier (§1.7);
  5. a digit, or . followed by a digit → a number (§1.8);
  6. /// → a triple-slash string (§1.9.2);
  7. " → a string (§1.9.1);
  8. otherwise → the longest operator or punctuation string from the fixed table in §1.11 that is a prefix of the input. If none matches, it is a lexical error ("invalid character") and one byte is skipped.

Rule 6 precedes rule 8, so a///b starts a string, not //.

1.6 Mathematical-operator characters

A byte pair b₁b₂ starts a math-operator character iff (with c = b₁·256 + b₂):

condition on c Unicode block covered
c & 0xFFE0 == 0xC2A0 U+00A0–U+00BF (Latin-1 punctuation)
c == 0xC397 / c == 0xC3B7 U+00D7 ×, U+00F7 ÷
c & 0xFFFE == 0xE286 U+2180–U+21FF (arrows; also number forms)
c & 0xFFF8 == 0xE288 U+2200–U+23FF (math operators, misc. technical)
c == 0xE29F U+27C0–U+27FF
c & 0xFFFC == 0xE2A4 U+2900–U+29FF
c & 0xFFF8 == 0xE2A8 U+2A00–U+2BFF

The token consists of the whole UTF-8 character: its length comes from the lead byte. If the very next byte is =, that byte is appended as well. The resulting string is interned:

  • if it names one of the three predefined Unicode operators · (U+00B7), ⊠ (U+22A0) or ⧢ (U+29E2), or their augmented forms ·=, ⊠=, ⧢=, the token is that operator;
  • otherwise the word gets identifier parse behaviour, so e.g. ∞ or → lexes as a one-character identifier. (∞= would likewise be an identifier word.)

1.7 Identifiers

identifier ::= letter alnum*

The identifier is maximal, but it also ends before any byte pair that starts a math-operator character (§1.6). Examples: x, x', x$1, a1b2, αβ (non-ASCII letters are letters), x'''.

An identifier word whose string was given special parse behaviour (the reserved words of §2.3, e.g. if, then, and, not, SPACE) is lexed exactly like an identifier. Only its parse information differs. This is how keywords are implemented: every keyword is simply an interned word with non-default parse information.

1.8 Numeric literals

number     ::= int-lit | real-lit
int-lit    ::= decimal | "0" ("b"|"B") bin+ | "0" ("o"|"O") oct+ | "0" ("x"|"X") hex+
decimal    ::= digit+
real-lit   ::= mantissa [ "p" digit+ ] [ ("e"|"E") ["+"|"-"] digit+ ]
             |  decimal "p" digit+ [ ("e"|"E") ["+"|"-"] digit+ ]
             |  decimal ("e"|"E") ["+"|"-"] digit+
mantissa   ::= digit+ "." digit*          -- "." not followed by another "."
             | digit* "." digit+

Exact algorithm (lex.d:336):

  1. If the first character is 0 followed by b/B and a binary digit, consume the radix prefix and all binary digits. Likewise o/O with octal digits and x/X with hex digits. Otherwise consume all decimal digits. (A leading . consumes no digits here.)
  2. Let c be the next character. The literal is real iff
    • the literal was decimal (no radix prefix) and c is . not followed by another ., or c is p, or c is e; or
    • c is E, regardless of radix. Quirk: 0b1E5 therefore lexes as one real-literal token. Its accidental conversion result is outside the established PN domain; PS rejects it during decoding (DEV-REAL-RADIX, §0.3).
  3. For a real literal, consume in order: an optional . and following digits; an optional p that MUST be followed by at least one digit ("precision missing in floating point constant"); and an optional e/E that MUST be followed by digits, optionally signed ("exponent missing in floating point constant").
  4. If a . immediately follows a real literal, a warning is issued. If a letter immediately follows any number (and does not begin a math-operator character), a warning is issued ("character 'x' immediately following number"). The letter still starts a new token, so 2x means 2 x (application, §6.3).

Consequences: 1..3 is 1, .., 3 ✔. 1. is a real ✔. .5 is a real ✔. x.5 is x followed by the real .5.

Values.

  • int-lit: an arbitrary-precision integer (ZZ), read in the indicated radix. Decimal literals with leading zeros are still decimal (007 = 7).
  • real-lit: a value of class RR. The precision is the number after p (in bits), or else the default precision current at lowering (53 unless changed). The rest of the literal, with the p… part removed, is rounded to that precision as a decimal floating-point number (MPFR mpfr_set_str, base 10). If the precision after p overflows, evaluating the literal produces the error "expected precision to be a small non-negative integer".

Examples ✔: 1e3 → 1000 (an RR), 1p100 → 1 with 100-bit precision, 1.5p100e2 → 150, 0x1F → 31, 0b101 → 5, 0o17 → 15, 1e400 → 1e400 (MPFR has a wide exponent range).

1.9 String literals

1.9.1 Double-quoted strings

A string runs from " to the next unescaped ". It MAY contain raw newlines. The backslash escapes are:

escape meaning
\n \t \r \a \b \v \f LF, TAB, CR, BEL (7), BS (8), VT (11), FF (12)
\e, \E ESC (27)
\" \\ the character itself
\xHH the byte with hex value HH (exactly 2 hex digits)
\uHHHH the UTF-8 encoding of code point U+HHHH (exactly 4 hex digits). A high surrogate \uD8xx–\uDBxx immediately followed by a low surrogate \uDCxx–\uDFxx combines into one supplementary code point.
\o, \oo, \ooo the byte with octal value o… (1–3 octal digits, greedy; value taken mod 256)

Any other character after \ is a lexical error ("unknown escape sequence"). A \x or \u with too few hex digits is also an error ("expected N more hex digit(s)"). After a string error the lexer discards the rest of the line.

The value is a String, i.e. a byte string.

1.9.2 Triple-slash strings

/// starts a verbatim string: no escape processing takes place, and the content may span lines. Doubled slashes let the content include runs of three or more slashes. The exact algorithm (lex.d:116):

consume "///"
out := ""
loop
    ch := next character (consume it)          -- EOF here is an error
    while ch = '/' and the next three characters are "///":
        out := out + "/" ; consume 2 characters  -- ch is still '/'
    if ch = '/' and the next two characters are "//": break   -- closing "///"
    out := out + ch
consume 2 characters

Consequences: // inside is literal. Three consecutive slashes end the string. //// inside gives ///, and 2k slashes (k ≥ 2) give k+1. A string ending in 1, 2, 3, … slashes is written by closing with 5, 7, 9, … slashes. ✔ ///abc\d"e/// = abc\d"e.

1.10 Newlines and the obeylines mode

The lexer is called in one of two modes:

  • obeylines = true: a newline is returned as a NEWLINE token.
  • obeylines = false: newlines are skipped like white space, and the next real token gets followsNewline = true.

The parser (§2) decides the mode for each request. In short: newlines end statements at the top level of a source unit, and are white space inside brackets and inside most compound constructs.

The token peeked by the parser is cached. Once a token has been peeked in one mode, a later request returns the cached token whatever mode that request asks for.

2. Syntax

Source: parser.d, binding.d:150–376, parse.d:119–157.

The Macaulay2 grammar is defined by the stateful Pratt parser below. Prefix operators use max(context, own strength), juxtaposition is triggered by the following token, some operands may be empty, and newline sensitivity is contextual. No impossibility claim about context-free representations is needed. The EBNF in §2.9 is informative, not a substitute for the algorithm.

2.2 Parse information

Every word w carries four things:

  • lbp(w) (called precedence in the source): the left binding power. An infix or postfix occurrence of w continues the current expression only while lbp(w) > context.
  • rbp(w) (binaryStrength): the context in which the right operand of an infix w is parsed.
  • ubp(w) (unaryStrength): the context in which the operand of a prefix w is parsed.
  • prefix handler and infix handler: functions from §2.4.

Ordinary identifiers and all literals share one default: lbp = 62 (= precSpace), no rbp/ubp, prefix handler defaultunary, infix handler defaultbinary.

The finite action vocabulary is:

Leading = error | default | unary | nunary | nnunary | paren
        | if | while | for | try | catch | new | quote(policy)
Trailing = error | default | binary | nbinary | postfix | arrow
QuotePolicy = ordinary | currentLocal | global | threadGlobal
Profile = (lbp, rbp, ubp, Leading, Trailing)

None in a strength field is native nopr = -1, not another ordinary binding power. Parser reflection reports the native numerical strengths. paren uses the encountered opening spelling and the fixed matching map; copying its profile does not register a new delimiter pair. The four quotation policies belong respectively to symbol, local, global, and threadLocal and must not be interchanged.

2.4 The parsing algorithm (normative)

The parser keeps a one-token lookahead buffer (§1.10). peek(m) returns the buffered token, or lexes one in mode m and buffers it. next(m) returns and clears the buffer, or lexes one in mode m. ob is the obeylines flag, passed down unchanged except where stated.

parse(prec, ob):                       -- an operand is required
    t := next(false)                   -- the first token of an operand always skips newlines
    return prefix(t)(t, prec, ob)

nparse(prec, ob):                      -- an operand may be empty
    t := peek(ob)
    if lbp(t) > prec: next(ob); return prefix(t)(t, prec, ob)
    else:             return Dummy(position of t)

accumulate(e, prec, ob):               -- the infix/postfix loop
    loop:
        t := peek(ob)
        if lbp(t) <= prec: return e
        next(ob)
        e := infix(t)(e, t, prec, ob)

Prefix handlers:

defaultunary(t, prec, ob)  = accumulate(Token t, prec, ob)

                             else accumulate(Unary(t, nparse(ubp(t), ob)), prec, ob)  -- leading ","

    return accumulate(Parentheses(l, e, r), prec, ob)

    return Adjacent(lhs, prefix(t)(t, 61, ob))                          -- 61 = precSpace − 1

Error recovery. After a syntax error the parser discards input. In interactive or full-lines mode it drops the buffered token. Otherwise it skips tokens while lbp > prec. The whole statement is then abandoned (§7).

2.5 Derived rules and their consequences

2.5.1 Juxtaposition (application)

Juxtaposition is the infix handler default belonging to the following token. It fires only when that token has lbp > context and its infix handler is default. The tokens that can begin an argument by juxtaposition are therefore:

  • identifiers, literals, (, {, and the lbp-62 keywords (if, for, new, symbol, time, return, …). Here lbp = 62, so juxtaposition happens in any context below 62;
  • [ and <|, with lbp = 56. They start an argument only in a context below 56;
  • not, with lbp = 34.

The right operand is parsed at context 61, so juxtaposition is right-associative and binds tighter than every infix operator except those with lbp ≥ 62 (@@, the postfix operators, ^, _, ., #, …).

Examples ✔ (1.25.11):

source parse
f x y f (x y) — so f 1 2 fails, since 1 2 has no method
f(x)(y) f ((x) (y))
f x^2 f (x^2)
f x! f (x!)
a - b c a - (b c)
a b - c (a b) - c
a * b c a * (b c)
f -1 f - 1 (binary minus, because - has a binary handler)
#f x #(f x) (the ubp of # is 61 < 62)
-f x -(f x)
a*f[x] (a*f)[x] (the operand of * is parsed at 58 ≥ 56, so [ does not attach to f)
f[x] f [x] at top level

The word SPACE supplies the adjacency method key. Bare prefix SPACE is a syntax error, but a SPACE b is a valid binary expression, whose actor evaluates adjacency. symbol SPACE is valid. This retains the pinned-source correction from v1.0 R3.

2.5.2 Prefix operators

A prefix operator parses its operand at max(context, ubp), then keeps accumulating at the outer context. So -a*b = -(a*b) ✔, -a+b = (-a)+b ✔, -a^2 = -(a^2), -a! = -(a!) ✔, not a == b = not (a==b) ✔, not a and b = (not a) and b ✔, <<a<<b = (<<a)<<b ✔.

2.5.3 Postfix operators

a^b! = a^(b!) ✔. a!^b = (a!)^b ✔. a^~ b = (a^~) b ✔. x (*) is postfix (*).

2.5.4 Commas and semicolons

, (lbp 10) and ; (lbp 8) are n-operators: their right operand, and for , also the left operand (via prefix nnunary), may be empty. So (1,2,), (,1), (a;) and (1,,2) are all well-formed. , is left-associative. ; is right-associative, and it binds more loosely than ,: (a; b, c) = (a; (b, c)).

2.5.5 Keyword forms

In the grammars below, E_p is "parse(p, …)". Clause bodies are parsed at 12, so they extend over assignments and arrows (lbp 14) but stop at , ; then else do list except and closing brackets. "Mode f" means obeylines = false, and "mode ob" means the mode inherited from the context.

if-expr    ::= "if" E₁₂(f) "then" E₁₂(ob) [ "else" E₁₂(ob) ]
                   -- "then" is read in mode f; "else" is looked for with peek(ob)
while-expr ::= "while" E₁₂(f) ( "do" E₁₂(ob)
                              | "list" E₁₂(ob) [ "do" E₁₂(ob) ] )
for-expr   ::= "for" E₁₆(f)
                 ( "in" E₁₆(f) | [ "from" E₁₆(f) ] [ "to" E₁₆(f) ] )
                 [ "when" E₁₆(f) ]
                 ( "do" E₁₂(ob) | "list" E₁₂(ob) [ "do" E₁₂(ob) ] )
try-expr   ::= "try" E₁₂(ob)
                 [ "then" E₁₂(ob) ]
                 [ "else" E₁₂(ob) | "except" E₁₂(ob) "do" E₁₂(ob) ]
                                     -- except/do is not allowed together with else
catch-expr ::= "catch" E₁₂(ob)
new-expr   ::= "new" E₁₆(ob) [ "of" E₁₆(ob) ] [ "from" E₁₆(ob) ]
quote-expr ::= ("symbol" | "global" | "threadLocal" | "local") T
                 -- T: the next token (mode f); it MUST have type code id, i.e. an identifier
                 -- or an operator word: "symbol +" and "symbol SPACE" are valid
special    ::= ("time" | "timing" | "elapsedTime" | "elapsedTiming" | "profile"
                | "shield" | "trap" | "breakpoint" | "TEST") E_max(ctx,12)(ob)
control    ::= ("return" | "break" | "continue" | "throw" | "step" | "finish") [ E₁₂ ]

Every keyword form is followed by accumulate(result, context, ob), so for example (if a then b else c) + 1 works, and if a then b else c + 1 puts c + 1 in the else clause.

Consequences:

  • In for, the variable is parsed at 16, so it stops at in, from, to and when, which all have lbp 16. The in/from/to/when clauses stop at do/list. At most one of in or from/to is allowed.
  • new parses its clauses at 16, so new T + new T = new (T + new T) and new A === new A = new (A === new A) ✔. Write (new T) + (new T).
  • try x then y, try x else y, try x then y else z, try x except e do y and try x then y except e do z are the only combinations (parser.d:454).

2.5.6 Function literals

The parser produces Arrow(lhs, parse(13,ob)) without validating the parameter tree. The body therefore swallows assignment and nested arrows but stops at commas/semicolons. f = x -> x, 1 is (f = (x -> x)), 1. Parameter validity is a binding rule:

  • A bare id atom is one rest parameter receiving the whole argument.
  • Any EmptyParentheses node gives zero fixed parameters.
  • Any Parentheses node accepts the same fixed-parameter token/comma-spine grammar: an id atom, or a canonical-comma Binary with a recursively valid left spine and an id right child. Duplicates, omitted operands, literals, nested delimiter nodes, and other operators are rejected.

The pinned binder does not inspect the delimiter kind here: round, square, brace, and angle-bar forms are accepted for this parameter-tree role. This is not a promise that a list/array value is an argument tuple. (x) -> body is a fixed-one-argument function; x -> body is a rest-parameter function. The distinction survives lowering.

2.5.7 Newline sensitivity

Statements (§2.6) are parsed with obeylines = true. As a result:

  1. A NEWLINE token (lbp 8) ends the current top-level statement, like ;, unless the parser is currently in a sub-parse run in mode f. Those are: bracket contents, the predicate of if/while, and the variable and in/from/to/when clauses of for.
  2. The first token of every operand is fetched with next(false), so a line that ends with a binary or prefix operator (or ->, =, then, do, , …) continues on the next line.
  3. Outside brackets, a line that begins with a binary operator does not continue the previous statement.
  4. else, the do after list, of, from (after new), and then/else/except after try are looked for with peek(ob). At top level, then, else at the start of a new line is not attached to a preceding if: ✔ the if statement ends at the newline and the next line gives "syntax error at 'else'". Inside parentheses it is attached normally.
  5. Inside brackets a newline is white space, except that a token that would start a juxtaposition after a newline is an error ("missing semicolon or comma on previous line?"). So (f\n x) is an error, while (f\n + x) is f + x.

2.6 Statements

A source unit is a sequence of statements, parsed by the loop of §7:

unit      ::= { NEWLINE | end-of-cell | statement terminator } EOF
statement ::= E₈   (parse(8, obeylines = true))
terminator::= ";" | NEWLINE | end-of-cell | EOF

After a statement is parsed, the next token MUST be a terminator. Anything else, necessarily a right bracket, gives "syntax error: unmatched )". A statement terminated by ; is evaluated with the NoPrint protocol (§7). A semicolon at the start of a statement is not skipped: ;1 and the second semicolon in 1;;2 are syntax failures in the source-unit driver. The parse utility is a different observation surface and must be tested separately. Audit F03

2.8 Operator words usable as values

Any operator word can be quoted with symbol op to obtain the corresponding keyword value. Keywords are used as method keys (§6.5).

3. Names, dictionaries and scopes (binding)

Source: binding.d:418–954, expr.d:47–160.

Between parsing and evaluation, each statement's parse tree goes through a binding pass (localBind). It resolves every identifier token to a symbol and allocates storage for local variables. Binding errors are reported, and the statement is then not evaluated.

3.1 Symbols

A symbol is a named storage location. Its attributes are: its name (word), the position of its definition, the frame id of the scope that owns it, an index within that scope's frame, a protected flag, a thread-local flag, and flagLookup, which produces a binding error when the flagged occurrence is looked up. Stable declaration/activation identity is separate from assignment permission and the user-visible isMutable predicate (§5.3).

The value SymbolClosure(frame, symbol) is how a symbol appears at run time (class Symbol, or Keyword for operator words and keywords, §5.4).

3.2 Dictionaries

A dictionary stores name-to-symbol entries, not just a deduplicated finite map. It has a frame id, an entry count, a protected flag, and an outer dictionary. Repeated := can add another entry with the same name. Lookup selects the first matching entry under the native entry order; counting/enumeration must retain the shadowed entries (§3.8). The outer link may be self for the outermost scope.

There are four kinds:

  • Global dictionaries (frame id 0). They are chained together: the chain is the dictionaryPath, with the current package's dictionary first and Core's later. All global symbols share one global frame. Thread-local global symbols live in a per-thread frame.
  • Static local dictionaries. One is created for each file being loaded, for each string evaluated by value, and for each interactive session and debugger level. It has a single frame that grows as symbols are added. Its outer link is itself, so lookup falls through directly to the global chain.
  • Transient local dictionaries, created by binding for function literals, for loops and try … except. Each run-time activation gets a fresh frame, except in the for case (§6.9).
  • The dummy dictionary (internal).

3.3 Name lookup

To bind an identifier token t in dictionary D:

  1. If t is a numeric literal, do nothing.
  2. Walk D, D.outer, … until the chain ends, then walk the global chain. The first symbol named t found is the binding.
  3. If no symbol is found, a new global symbol is created. It is created in the first non-protected dictionary of the global chain, normally the current package's or User's. Its initial value is the symbol itself, unless the name is not a valid symbol name or the symbol is thread-local; the initial value is then null. So an undefined identifier evaluates to itself: z ⇒ z ✔. This happens at binding time, even for code that is never executed.

Operator tokens are looked up the same way, but a missing operator is never created. It is an error ("undefined symbol"), which cannot happen for the built-in operators.

3.4 Scopes

Only these constructs open a new (transient) scope:

construct scope contains bound in the enclosing scope
params -> body parameters, then body —
for v … when W list L do B v, W, L, B the in, from and to clauses
try P then S except v do B v, B P, S

if, while, catch, new and parentheses do not open scopes. A := anywhere inside a function body, even in an unexecuted branch, allocates a slot in that function's frame.

3.8 Dictionary entries, aliases and visibility history

DICT-HISTORY. Separate three observations: name lookup, retained entry storage, and frame layout. A fresh local declaration allocates a new SymbolId/slot and prepends a new entry even when that name exists. It does not delete the earlier entry or rewrite old code. #dictionary counts retained entries; dictionary enumeration must not silently deduplicate same-name entries. values returns symbol/keyword references, not cell contents; pairs associates each entry's lookup spelling with its symbol reference. A fast name index is a view of the entry store, not a replacement for its cardinality/history. Exact enumeration order follows the implementation's declared native/portable observation policy, not an invented universal sorted order. Audit F15

The global path is ordered, contains global dictionaries without duplicates, and has a writable dictionary. Implicit creation chooses its first unprotected member. Visibility changes affect later resolution only; previously resolved references retain their targets. A declaration's original scope is provenance, not an exclusive package-ownership claim.

For d#"name" = s: evaluate dictionary, key, RHS; validate shapes and compatible frame; require an unprotected dictionary; call first-wins word registration with the canonical word's profile; check key absence; insert an alias entry for the same symbol. No canonical renaming, arbitrary parse callback, or punctuation-trie extension occurs. A duplicate-key failure can occur after word registration. Earlier word history therefore matters even after unsuccessful alias insertion. The profile used on an occurrence and the canonical profile used by symbol reflection need not be the same.

Removing visibility does not invalidate a symbol value or direct reference. Open contract OC-DICT: exact erase behavior across canonical-name buckets, aliases, retained entries and all rehash/enumeration effects must be fixed before reflective dictionary conformance is claimed; replacing this with “delete all aliases” is not authorized.

3.9 Logical state and address identity

The semantic state contains exact word history, dictionary entries/path, declarations, logical activation/storage graphs, values/objects, source-unit state, hooks, and reached effects. A declaration has stable canonical spelling, slot/provenance, protection and thread metadata. A reified symbol denotes a declaration and a particular activation.

An ordinary reference can lower to a direct global location, a lexical (depth,slot), or a thread-global slot resolved in the executing thread. Reification recovers the selected declaration and live address without reading the stored value. Thread reification captures the current thread's cell; ordinary thread-global reads remain thread-relative.

(FrameId,slot) is an adequate logical cell address. A machine may use flattened CellIds, inline slots, or metadata side tables; it need not allocate both a frame object and an additional object for every cell. Logical identities cannot be reassigned while still observable. Physical allocation and reclamation are architecture choices constrained by symbols, closures, dictionary values, snapshots, and reflective backing views (§5.7). Audit F23

4. From parse tree to code

Source: convertr.d. The bound tree is translated into a tree of code nodes, which §6 evaluates. The translation fixes several syntactic identities, and an implementation MUST respect them whatever its internal representation.

4.1 Sequences of expressions

separated(e, sep) flattens a ,- or ;-tree into a list of elements:

  • Binary(a, sep, b) → separated(a) ++ separated(b);
  • Unary(sep, b) (a leading separator) → [null-code] ++ separated(b);
  • Dummy (an empty operand) → [null-code];
  • anything else, including a parenthesized expression → [convert(e)], with no further flattening.

Consequences ✔: (1,) is the 2-element sequence (1, null). (,1) = (null, 1). (1,,2) = (1, null, 2). #(1,2,) = 3. (a;) evaluates a and yields null.

4.4 Resolved code and operator identities

The logical code vocabulary is: constants/error constants, direct reads, symbol reification, sequence/list/array/angle-bar construction, semicolon blocks, function templates, application, unary/postfix and binary actor calls, assignment plans, augmented assignment, If, While, For, Try, Catch, and the four New combinations. This covers every tree family without requiring one native D constructor per optimized instruction.

A function template carries a declaration/layout identity, fixed/rest convention, parameter count, layout, body, code identity and source mapping. Bare break/continue preserve an omitted operand, distinct from an explicit expression evaluating to null. In separators and containers the same Dummy tree instead lowers to an ordinary null constant.

Assignment plans distinguish variable, recursive parallel, index, globally quoted field, unary/postfix/binary method target, application target, and constructor target. Mixed nested targets retain bound code and shape until the native runtime target check; they are not restricted to names. Tables §4.3 and §6.6 determine each plan's behavior.

Keep encountered word identity and resolved SymbolId through lowering. Canonical source commas/semicolons flatten; aliases do not become those separators merely by copying profiles. Canonical source =/:= determines declaration/assignment lowering, while native dot conversion additionally tests the selected dot symbol. Inconsistent alias-created global-key references must not be reinterpreted as convenient valid fields (§0.3).

5.2 Classes, parents and types

Every value x has a class, class x, which is always a HashTable. Every HashTable has a parent field. The ancestors of a class C are C, parent C, parent parent C, …, ending at Thing, whose parent is Thing itself.

  • ancestor(A, B) is true iff B is among the ancestors of A.
  • instance(x, T) is ancestor(class x, T).
  • parent x is x's parent field if x is a hash table, the wrapped value's parent for a SpecialExpr, and Nothing otherwise.
  • A type is a hash table whose class is Type (or a descendant). Types are mutable hash tables, since parent Type = MutableHashTable. Methods are stored in them (§6.5).

5.4 Symbols and keywords

symbol x (or evaluating an unassigned global x, §3.3) yields a SymbolClosure. Its class is Keyword if the word has non-default parse information (all operators and keywords, e.g. symbol +, symbol if, symbol SPACE). Otherwise the class is Symbol. The value stored in a symbol is read with value s and written with s <- v (§6.10).

Two symbol closures are ===-equal iff they have the same symbol and the same frame. Ordinary global symbols use the global frame; thread-global reification uses its actual thread frame.

5.5 Strict equality ===

x === y (and its negation x =!= y) does not use user-defined equality methods. The ordinary core cases below return Booleans. Do not infer totality across external engine equality failures or Error objects embedded in composites; those boundary cases remain OC-EQUALITY. The following cases summarize equality.dd:

  • identical representations → true;
  • ZZ/ZZ, QQ/QQ: numeric equality. Different numeric representations are never ===, so 3 === 3.0 is false ✔ and 1/2 === 0.5 is false ✔;
  • RR/RR, CC/CC, RRi/RRi, CCi/CCi: strict equality of value and precision. ✔ 1.0p100 === 1.0p53 is false, although == is true;
  • String/String: byte equality. Net/Net: equality of rows and baseline;
  • Sequence/Sequence: equal length and elementwise ===;
  • List/List: both immutable, same class (by ===), equal hash, equal length, elementwise ===;
  • HashTable/HashTable, ordered branch: object identity succeeds first; unequal hashes fail; different class or parent identities fail; then hash zero with the exact CacheTable class succeeds. Only after that special case do mutable tables fail distinct- object comparison. Ordinary immutable tables proceed to the native structural entry comparison. A subclass is not automatically admitted by the exact-class cache branch. In particular, direct CacheTable objects with different parents are unequal. Audit F10;
  • SymbolClosure: same symbol and frame. DictionaryClosure: same frame and dictionary. Pseudocode: same code (and frame);
  • SpecialExpr: same class and === wrapped values;
  • functions, files, null, Booleans, mutable engine objects: only identity;
  • engine objects: engine equality where defined;
  • anything else, including values of different representations → false.

6.0 Configurations, effects and contract boundaries

The interpreter can be specified using configurations Eval(code, environment, continuation), Deliver(completion, continuation), HostRequest(request, continuation), and Done(completion), each paired with reached state and ordered effects. Continuations must distinguish at least strict operand sequencing, function return, each loop form/clause, try suppression/catchability, comparison second-evaluation inspection, assignment-hook stages, and source-unit stages. These are semantic distinctions, not mandatory machine allocation types.

Every defined transition retains state already produced. An implementation budget suspension is separate from a language completion; it cannot be caught by M2 try or turned into null. A pending host request is not a completed operand value. Default strict propagation applies only where a more specific actor/continuation rule does not say otherwise. In particular §§6.9.1, 6.9.2 and 6.10.1 are not instances of a uniform “catch all control at the innermost construct” rule.

The attached evidence does not supply all native primitive/actor transitions. §8 names those open contracts. Thus this is a single partially closed transition contract, not a claim that an ActorId or HostRequest signature already defines every transition. Implementations must report rule-level coverage. A future refinement theorem must name the closed subset it covers until those obligations are discharged. Audit F24

6.1 Environments

Evaluation happens relative to a current frame. A frame is a vector of values plus a link to its outer frame. A variable reference compiled as (depth d, index i) reads slot i of the frame d links out. Globals live in the single global frame (per-thread for threadLocal symbols). A slot never assigned holds null.

Required observable properties:

  1. Closures capture frames by reference. ✔ x := 10; f = () -> x; x = 20; f() ⇒ 20. ✔ g = () -> (n := 0; () -> (n = n+1)); c = g(); c(); c(); c() ⇒ 3.
  2. Each function call has a fresh logical activation for its parameters/locals. Native empty-frame elision and the exact reflective chain must be preserved by the observation projection (§5.7); a logical activation is not a mandate to expose an extra frame.
  3. A for loop allocates one frame for the whole loop. The loop variable is overwritten in place on each iteration, so closures created in different iterations share it. ✔ L = for i from 1 to 3 list (() -> i); apply(L, f -> f()) ⇒ {3,3,3}.
  4. A try … except v do B allocates a frame for v when the handler runs.

Implementation note: the reference implementation computes frame depths statically and omits frames for scopes with no variables. Any environment model that gives the properties above is acceptable.

6.2 Outcomes: values and abrupt completions

Evaluation of any code yields either a value or an abrupt completion. The reference implementation represents both uniformly: an abrupt completion is an Error record whose message field distinguishes these kinds:

error failing operations, error(…) (library) message, optional value, position try, trap, ?? (§6.9); otherwise it reaches the top level, which prints it (§7)
return return [e] value (null if omitted) the innermost enclosing function application; also load/value/the top level (§7)
break break [e] value or omitted operand The loop/clause cases in §6.9.1; domain expressions are outside those handlers
continue continue [e] value or omitted operand Only the loop clause-specific handlers in §6.9.1; native combining functions have their own primitive contracts, not a universal loop rule

These rules follow:

  • Strict operand continuations propagate an abrupt result while retaining reached effects. This is not universal: the second left evaluation of <=/>= is inspected without a blanket Error/transfer check (§6.10.1). Clause-specific control, native callback primitives, and augmented-target schedules have their own rules. Ordinary binary evaluation is left first only where the actor specifies that schedule.
  • try excludes return, break, either continue form, unwind, and throw; step and finish are not in that exclusion set. Catchability also depends on suppression/interrupt state (§6.9.2), not solely on a proposed Error-versus-Control datatype.
  • A control abrupt completion that escapes to where no construct handles it (for example break outside a loop) is reported at top level as "unhandled break command" and so on.
  • There is a recursion limit, 300 by default: a function application at a deeper nesting depth fails with "recursion limit of 300 exceeded". Implementations SHOULD provide a comparable limit.

When an error propagates out of code with a known source position and has not been positioned yet, the position is recorded. The error is printed immediately with "--back trace--" lines while it unwinds, unless errors are suppressed, as they are inside try (§7.3).

6.3 Function application

f a (apply): evaluate f first.

  • If f is a FunctionClosure with n declared parameters:
    • if the argument code a is a sequence code ((a₁,…,aₖ) with k ≠ 1, including ()), evaluate the k items left to right to get the arguments;
    • otherwise evaluate a. If the value is a Sequence, its elements are the arguments. Otherwise the single value is the one argument.
    • Rest parameter (x -> …): x is bound to the whole argument. That is a Sequence when there are 0 or ≥ 2 arguments or a sequence was passed, otherwise the single value. ✔ f = x -> x; f() ⇒ (), f(1,2) ⇒ (1,2).
    • Ordinary parameters: the argument count MUST equal n, else the error "expected n argument(s), but got k". A single non-sequence argument counts as 1. ✔ f = (x,y) -> x+y; s = (3,4); f s ⇒ 7. f {1,2} is an error, since a list is one argument.
    • A fresh frame (§6.1) is created whose outer frame is the closure's frame. Parameters fill slots 0…n−1 and all other slots are null. The body is evaluated in it. A return completion becomes the result value. Other abrupt completions propagate.
  • If f is a CompiledFunction or CompiledFunctionClosure: evaluate a to a single value (a sequence stays a sequence) and pass it to the built-in.
  • If f is a SpecialExpr wrapping a function: apply the wrapped function as above. If it wraps a non-function: dispatch as in the next case.
  • Otherwise evaluate a to v and call the binary method for SPACE on (f, v) (§6.5.1), with keys (SPACE, class f, class v). If none exists and f is a symbol, the error is "symbol 'f' has not been defined as a function". Otherwise it is "no method for adjacent objects". Example: R x where R is a ring is a library method on (Ring, …).

Implementation note: the reference implementation evaluates a tail call g x at the end of a one-argument function body without growing the stack. It does not do this for general calls.

6.4 Errors as values

try … except e do … and trap expose an error as a value of class Error. If the error's value field holds a hash table descending from Error, the class is that table instead (classes.dd:122). How errors are created and presented (error, the Error subclasses, message formatting) is library-defined.

6.5 Operators and method dispatch

Every operator is implemented by a built-in routine. Many routines first handle some combinations of basic types directly (§6.10), and otherwise dispatch to a method stored in the class hierarchy. The method key of an operator is its keyword symbol (symbol +, …).

6.5.1 Lookup

  • Unary method for operator op on x: search the ancestors of class x, most specific first, for key op. The same lookup finds a method function keyed by a function f, as installed by f T := ….
  • Binary method for op on (x, y):
    for L in ancestors(class x):          -- most specific first
    for R in ancestors(class y):
        if the key (op, L, R) is present: return its value
return none
    The entry for (op, L, R) is stored in whichever of L, R has the greater internal hash. An implementation MAY store it anywhere, as long as lookup follows the loop order above.
  • Ternary / quaternary methods, keyed (op, A, B, C[, D]), are searched analogously with nested loops, first argument outermost.
  • Nullary methods (f() := …) live in a global table keyed by (f).

When no method is found, the result is an error such as "expected pair to have a method for '+'" (binary) or "expected a method for 'op'" (unary).

6.5.2 Calling

A found method m is applied like a function (§6.3), to the single argument x (unary), or to the arguments (x, y) (binary), and so on.

6.5.3 Installation: := on operator forms

6.5.5 One authoritative method/object store

METHOD-AUTHORITY. Method entries are the actual observable entries of the native class/object tables. Nullary methods and typical-value records are likewise designated user-visible table objects, not independent hidden semantic registries. Direct allowed M2 mutations of those entries affect subsequent lookup immediately. A separate index or dispatch cache is derived, and may be invalidated/rebuilt; it cannot disagree with the visible table and remain authoritative. Audit F18

For binary methods use the native placement policy already specified in §6.5.1: the entry resides in the greater-hash operand class (the RHS table on a tie in the audited binary branch), and lookup uses the same placement rule while traversing ancestors. Unary entries are in their class table. Higher-arity placements must preserve the native observable table policy, not merely produce the same call result.

Cache guards cover method-entry writes, class/parent changes and all other mutable lookup dependencies. A conservative global epoch is an implementation option, not an extra language object. Failed installation's effects on typicalValues, including ignored recursive results in Option wrappers, remain OC-INSTALL until independently contracted.

6.6 Assignment

Assignment results are per form, not universally the supplied RHS:

Form Result
Direct variable or element store Stored value on success
Custom operator/application/indirect assignment method The invoked method's result
Augmented method that intercepts fallback That method's result, with no implicit fallback store
Parallel assignment Actual per-target results; a single target is unwrapped, multiple targets preserve the specified sequence/list result class

6.6.1 Variables

ASSIGN-HOOK-SCHEDULE. For x = e or a resolved variable x := e, evaluate e first. A local assignment updates its addressed cell directly. For a global assignment:

  1. Check symbol protection. Failure returns the protected-variable error without running hooks or performing the final store; already completed RHS effects remain.
  2. Read the old value and look up/capture its class's GlobalReleaseHook now.
  3. Look up the symbol-specific entry in globalAssignmentHooks under symbolBody x. If present, invoke its function, or listed functions in order, as (symbol x,new).
  4. Invoke the captured release method, if any, as (symbol x,old).
  5. Now look up the new value's class GlobalAssignHook, and invoke it as (symbol x,new).
  6. Store the new value in the global/thread-global cell and return it.

An error stops subsequent steps, but does not undo earlier RHS/hook mutations or output. Invocation order is not lookup order: a symbol-specific hook that replaces the release method does not change the method already captured for this assignment. Changes to the new assignment method made before step 5 do affect that later lookup. Audit F08

Indirect <- remains distinct. Evaluate its left then right. If the left value is a symbol and a symbol-specific hook entry exists, use the native global-assignment routine. Otherwise check protection and directly update the captured symbol cell; do not add the class hook path merely because the symbol is global. Non-symbol left values use the specified <- method path. This preserves v1.0 R9 rather than merging all stores.

6.6.2 Parallel assignment

Evaluate RHS once. Let n be the number of target code items after immediate separator flattening. If n=1, a scalar RHS is treated as one value; a Sequence or List RHS must have exactly one element, which is selected. For other counts a Sequence or List must have length n. A List records its class for reconstruction, then supplies its elements.

Assign each target in order using the corresponding direct-store, custom assignment, method-installation, recursive delimiter, constructor, or omitted-target rule. An omitted target returns that supplied item without a store. Stop on the first failure, retaining earlier effects. Targets can be mixed and nested as §4.3 specifies.

The result collects the returned per-target results, not a blind copy of the original RHS. For n=1, return the single result directly—even when RHS was a one-element List. For n≠1, return a Sequence, or a List of the remembered RHS class. With zero targets and a matching empty RHS, return the corresponding empty result. Audit F13

(a,b)=(b,a) swaps. A length mismatch is an error. (x)=(5,) fails because (5,) has two elements. Unsupported nested target kinds fail at their native runtime check; the parser must not eliminate mixed target shapes in advance.

6.6.3 Element store: x # k = e, x . s = e

Evaluate x, then k (or take the symbol s), then e:

  • mutable List: k MUST be a small integer. A negative k counts from the end. Storing past the end extends the list, padding with null ✔. An immutable list gives the error "assignment attempted to element of immutable list". A Sequence gives an error.
  • HashTable: store the (key, value) pair. The table MUST be mutable, else "attempted to modify an immutable hash table".
  • Database: string key and string value.
  • Dictionary: d#"name" = s adds an alias name for the existing symbol s. The dictionary MUST be unprotected, and the name MUST be new.
  • For x.s = e, x MUST be a hash table.

6.6.4 Assignment to operator forms with =

x op y = e looks up the binary method ((op, symbol =), class x, class y) and applies it to (x, y, e). op x = e looks up the unary method ((op, symbol =), class x) and applies it to (x, e). f x = e uses op = SPACE. x and y are evaluated before e. With no method the error is "expected pair to have an assignment method for 'op'".

6.7 Augmented assignment L op= e

Augmented assignment is not a universally valid macro L = L op e. It has native target- specific evaluation, method interception, caching and fallback rules.

AUGMENT-SCHEDULE. Obtain the exact registered base operator for the augmented symbol. Sequence/list/array/angle-bar target code uses recursive augmented parallel assignment; RHS values are evaluated once and supplied itemwise under its arity/result rules. A single augmented parallel target wraps its RHS as one item; it does not inherit every ordinary parallel unpacking rule. Audit F12, F13

For a scalar target:

Target path Initial evaluation/selection order
Ordinary variable/other expression Evaluate L once to its old value; evaluate RHS when interception or fallback needs it
container # key, where container evaluates to a HashTable Evaluate container → evaluate RHS → evaluate key → lookup/lock. Cache container, key and RHS for this path
container . name, with a HashTable Evaluate container → RHS → form globally reified field key → lookup/lock
#/dot target whose container is not a HashTable Reuse the initially evaluated container for that first target read; preserve the subsequent fallback target schedule rather than applying the hash-table cache policy
L ??= e Error-suppress/nullify L first. A non-null result returns immediately without RHS/store. The null case takes the native coalescing-assignment fallback path, not the ordinary old-value binary path

For the ordinary augmented path, after obtaining the old value, look up a unary method under the augmented operator key in that value's class. If present, obtain RHS if not already cached and invoke the method on old value and RHS. A normal result completes the operation with no implicit store unless it is a SymbolClosure whose canonical word bytes are exactly Default. That test does not require a particular global SymbolId, namespace, or activation. Such a symbol requests fallback. An abrupt method result propagates after required lock cleanup. Audit F11

Fallback computes the ordinary base actor on the already obtained old value and cached RHS/code, then assigns via the native target rule. For the hash-table path, update the cached entry and unlock without re-evaluating container/key. 7.1 The read–eval loop

UNIT-STEP. A file, value string, interactive session, or frontend unit has a static local scope/frame, cursor with one-token lookahead, last value and output policy. The driver does:

EOF -> finish with lastvalue or null according to returnLastvalue
NEWLINE or EOC -> consume and repeat
otherwise:
    tree = parse(8,true)
    consume one terminator from { ';', NEWLINE, EOC, EOF }
    bind tree in this source-unit scope
    if binding failed: follow §7.2 and do not execute this tree
    lower at current literal precision
    run unqualified BeforeEval(null)
    execute according to the stage-failure policy below
    handle completion or printing protocol
    resume from reached state and cursor
