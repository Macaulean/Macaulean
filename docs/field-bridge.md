# Fields, polynomial ideals, and checked Gröbner bases

The bridge gives finite M2 worksheet objects mathematical meanings in Lean. M2
source code computes candidate answers; Lean checks explicit evidence about those
answers. This does not require formalizing the whole M2 interpreter or trusting
its Gröbner basis algorithm.

The first supported coefficient families are exact rationals (`QQ`) and prime
fields (`GF(p)`). Polynomial rings retain their coefficient field, ring identity,
ordered variables, and fixed graded reverse lexicographic (grevlex) order.
Extension fields F_(p^k) are a follow-up.

## Worksheet to Lean

```lean
import MacauleanMathlib
open M2

K = GF(5);
R = K[x,y];
I = ideal(x^2-y,x*y-1);
f = x^3-1;
G = gb I;

#m2_export "K" as K_math
#m2_export "R" as R_math
#m2_export "I" as I_math
#m2_export "f" as f_math
#m2_membership "f" in "I" as f_in_I
#m2_groebner "G" for "I" as gb_correct

example : Lean.Grind.Field K_math.Carrier := inferInstance
example : K_math.characteristic = 5 := rfl
example : I_math.Member f_math := f_in_I

example :
    (Macaulean.Verification.Mathlib.grevlexOrder 2).IsGroebnerBasis
      (Macaulean.M2.Verification.GroebnerViews.basisMeaning gb_correct.idealEquality.basis)
      (Macaulean.M2.Verification.GroebnerViews.idealMeaning gb_correct.idealEquality.ideal) :=
  gb_correct
```

Replace `GF(5)` with `QQ` for rational coefficients. Use an assigned coefficient
field as above, or parenthesize a computed field: `(GF(5))[x,y]`. The existing
parser's unparenthesized application/bracket precedence is not a complete model
of native M2 syntax.

`#m2_export "binding" as name` accepts coefficient fields, polynomial rings,
polynomials, and finitely generated ideal presentations. It publishes `name`,
the immutable runtime snapshot `name.source`, and a kernel-checked decoder equation
`name.source_eq`. Later worksheet assignments do not change these declarations.
They remain usable when imported into another Lean module.

Polynomial equality means equality of every coefficient, independent of ordering,
duplicate terms, or explicit zero terms. It is not equality of polynomial functions:
x^5-x remains a nonzero formal polynomial over F_5. An ideal means the mathematical
ideal generated by its presentation, not the generator list itself.

## What the proof commands establish

* `#m2_membership "f" in "I" as proof` checks an explicit expression of `f` as a
  polynomial combination of `I`'s generators. The theorem proves `I.Member f`.
  The `.polynomial`, `.ideal`, `.coefficients`, and `.checked` declarations retain
  the input snapshots and witness. Failure does not establish nonmembership.
* `#m2_ideal_equality "G" for "I" as proof` checks representation rows in both
  directions. Its theorem identifies the generated ideals. One containment,
  matching generator lists, or a runtime basis tag is insufficient.
* `#m2_groebner "G" for "I" as proof` additionally checks monicity and bounded
  zero-remainder representations for every S-pair. It proves that the candidate's
  leading terms generate the leading-term ideal of the original input ideal.
  The `.idealEquality` subtree records both containments and the candidate snapshot;
  `.pairRows` and `.pairs_checked` record the S-pair evidence.

The degree bounds matter. Every S-polynomial already belongs to the ideal generated
by its pair, even for a generating set that is not a Gröbner basis. A correct
membership identity alone is therefore not a Gröbner certificate. Tests include
this exact counterexample, as well as malformed rows and matrices.

The executable checker independently validates leading terms after normalization.
Its soundness theorem uses a grevlex monomial order proved to match the runtime
comparator and to be well founded. A proved Buchberger criterion connects the
accepted evidence to the leading-term-ideal property. Checks produce kernel proofs;
they do not use `native_decide`, extra axioms, or admitted proof holes.

## Lean to worksheet

`#m2_import term as "binding"` accepts a closed Lean coefficient field, polynomial
ring, polynomial, or finite ideal presentation. For example, after the worksheet
above:

```lean
#m2_import I_math as "Iagain"
Gagain = gb Iagain;
#m2_groebner "Gagain" for "Iagain" as certified_again
#m2_export "Iagain" as returned
example : returned = I_math := rfl
```

The supplied term can also be a newly constructed `RingPolynomial ring` or
`IdealPresentation ring`. See
[`MacauleanMathlibTest/MathematicalImport.lean`](../MacauleanMathlibTest/MathematicalImport.lean)
for complete QQ and F_5 examples built from Lean coefficient/exponent lists.

Importing a ring publishes its named variables. A fresh ring identity is reserved
so later worksheet rings cannot collide with it. Reusing an allocated identity
requires a matching existing runtime ring; conflicting identities, duplicate
variable names, and protected binding names are rejected atomically. To reuse a
worksheet ring, construct new Lean polynomials over its exported ring. To create
a new ring from Lean, choose an unused identity.

Evaluation only proposes the imported data. Before publishing it, the command
checks its equality to the Lean encoding in the kernel and records the source
and equation under the module's `M2Imports` snapshots. The `field_roundtrip`,
`ring_roundtrip`, `polynomial_roundtrip`, and `ideal_roundtrip` theorems prove the
corresponding decoder returns the supplied presentation.

These are explicit snapshots in Lean's M2 worksheet, not live synchronization with
an external M2 process. An arbitrary abstract Lean ideal need not have an executable
finite presentation; imports require concrete data.

## Implementation and boundaries

The core modules use Lean's core algebra classes and the project's sparse
polynomial representation. Import `Macaulean.Verification.CertificateCommands`
for membership/equality/export commands without importing Mathlib, and
`Macaulean.Verification.MathematicalImport` for reverse imports.

The proof-only `MacauleanMathlib` library pins Mathlib v4.33.1. It interprets the
same presentations as `MvPolynomial`, transports worksheet membership and ideal
identities, and provides Gröbner certification. The Buchberger theory is adapted
from Junyu Guo and Hao Shen's
[groebner_proj](https://github.com/WuProver/groebner_proj), with Apache 2.0 licensing,
[pinned provenance and local changes](../MacauleanMathlib/GroebnerTheory/README.md).
It does not require native compilation of all Mathlib modules.

Prime-field construction checks the inverse law for every residue and derives a
`Lean.Grind.Field` instance. This exhaustive first implementation is intended for
small characteristics, not fast primality testing. Composite characteristics,
zero, and one are rejected. Rational promotion into F_p is partial: denominators
must remain nonzero modulo p, so `(1/2)*x` works in characteristic 5 while `(1/5)*x`
fails. Mixed coefficient fields and incompatible ring identities are rejected.
The source reduction/Buchberger code is depth-bounded, and kernel checking also
has Lean's usual resource limits.

For compatibility when importing both libraries, the earlier factorization
predicates are now `Macaulean.Factorization.IsUnit` and
`Macaulean.Factorization.Irreducible`; add `open Macaulean.Factorization` to older
factorization examples. The factorization tactic behavior is unchanged.

`lake test` includes the bridge tests, standard-axiom audits, existing QQ regressions,
native M2 coefficient comparisons, prime-field comparisons over F_2/F_3/F_5/F_7,
QQ/F_5 Gröbner certificates, characteristic-two and zero/unit cases, import persistence,
reverse conversion, and negative certificate/ring checks.
