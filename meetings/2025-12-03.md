## Topics

### AI and Math Engagement Strategies

The meeting began with some technical difficulties as participants joined the live session. Matthew and Damiano discussed the JSON schema for MERDI, while Michael and Anton joined later. The group talked about scheduling conflicts due to finals week and upcoming conferences. Matthew shared updates from a recent NSF meeting and an advisory board meeting, highlighting the need to develop rules of engagement with corporate America regarding AI and mathematics. They briefly discussed companies like Harmonic and Logical Intelligence, which are working on AI models for formalizing mathematical problems.

### Formal Proof System Trust Verification

The group discussed concerns about formalizing natural language mathematics and the reliability of automated proof systems. Damiano shared an example where a cubic polynomial proof generated by a model contained warnings that cast doubt on its correctness, highlighting the need for better trust verification in formal proof systems. The team also examined a 10,000-line code snippet purportedly proving a mathematical conjecture, with Matthew noting that while the code was formally verified by Lean, there were questions about whether "sorry" statements and warnings should be treated differently in the verification process. Jay suggested the possibility of running Lean from the command line to verify proofs, and Matthew mentioned that Henrik Bovig was developing tools for running modules in clean environments.

### Lean Homework Tools Development Update

The team discussed the development and deployment of Lean homework tools, focusing on counteracting models that produce incorrect results. Jay reported progress on integrating Lean polynomial serialization with Macaulay 2, though the implementation is currently complex due to multiple branches that need to be merged. Damiano and Michael expressed interest in continuing the project despite current workload constraints, with Michael mentioning potential flexibility in his teaching schedule to allocate more time to the project.

### Project Flexibility and Code Challenges

The team discussed their interactions with Renfield, noting that the representative, Ralph, showed flexibility regarding their project's direction. Jay explained changes made to a pull request, including a method addition that was lost during rebase. Michael shared his experience trying to run Lean4 samples, including a Rubik's Cube example in VS Code, which failed due to outdated code and lack of Mathlib dependency.

### Rubik's Cube Code Error Investigation

The team discussed issues with the Rubik's Cube sample code repository, which has a type mismatch error in its Lean file. Damiano suggested that the error might be due to an unnoted update, while Matthew noted that the code is 3 years old and likely incompatible with current widget definitions in VS Code. Michael agreed to investigate further, as he was interested in understanding how the language server in VS Code could be used to display other content. Jay mentioned that he had managed to get the code working again.

### Lean-Macaulay 2 Communication System

Jay explained the development of a system that allows communication between Lean and Macaulay 2 using MERDI data format, focusing on the technical aspects of data transfer and format conversion. He highlighted that the current implementation is primarily about establishing the necessary plumbing, with no significant mathematical innovation, and discussed some minor issues such as the need to convert data to a string format for Macaulay 2 and resolving discrepancies in coefficient and monomial order between different implementations. Damiano noted that while the innovation is not major, the system works and confirmed that it currently uses integer coefficients.

### Polynomial Conversion Between Systems

Jay and Damiano discussed the challenges of converting polynomial types between Lean and Macaulay 2 using the MERDI format. They explored the possibility of adding a namespace option to facilitate the conversion process. Jay outlined the next steps, including creating an echo function to send polynomials between the two systems and implementing appropriate methods for polynomial factorization. They also discussed the limitations of using JSON for serialization and the need for a more systematic approach to type conversion. Damiano suggested creating a list of polynomial rings in Lean to facilitate the conversion process.

### Lean-Macaulay 2 Type Mapping

The team discussed the current implementation of type mapping between Lean and Macaulay 2, where a class serves as a basic mapping mechanism between string types. They agreed that while this approach might be sufficient for their current applications, it could become problematic with more complex types, particularly parameterized types. Douglas explained that MRD format uses unique identifiers generated through a random number specification, with a very low chance of collisions, and Damiano proposed embedding Lean's unique identifiers within these MRD UIDs to facilitate easier matching between the two systems.

### Lean Garbage Collection Discussion

The team discussed garbage collection in Lean, with Jay explaining that Lean uses reference counting but avoids loops due to well-founded recursion. They explored how to handle object lifetimes when passing data between Macaulay 2 and Lean, with Jay suggesting keeping all objects alive as a temporary solution. The group agreed to meet next week at the same time, with Michael noting his availability would be limited due to upcoming travel. They also discussed error handling in Macaulay 2, with Douglas presenting a pull request that addresses error message capture within try statements.
