## Summary

The team discussed several topics related to their ongoing project involving polynomial representations and Lean implementation. They addressed the need to improve the interface between Lean and Macaulay 2, with Jay proposing a new polynomial representation that would package computations into a single MRDI file rather than separate files. The group also discussed the use of Native Decide for verification and potential collaboration with AI for verifying C library implementations. They explored the challenges of using quotient types in Lean and considered mimicking Macaulay 2's operations for faster computations. The team reviewed the current state of their Merdi package updates and discussed plans for the upcoming release of Macaulay 2, which will include improved error message handling.

## Topics

### AI for Math Event Planning

The team discussed attending an AI for Math event in London scheduled for September 17-18. Matthew volunteered to attend and confirmed he could go, while Michael indicated he might be able to attend but needed to check his schedule due to potential travel to Japan. Anton mentioned he couldn't attend due to a teaching commitment on Friday, and Damiano was unable to attend due to existing travel plans. ### Polynomial Representation and Interface Updates

Michael discussed the possibility of buying out of a class and using the funds for summer support, planning to consult with someone at Renfo about this decision. Jay proposed cleaning up the interface by combining polynomials into a single type that represents the problem and certificate, rather than sending them as separate Verdi objects. The team discussed potential changes to the polynomial representation, including handling coefficients and monomial orders, with Jay suggesting that Cloud Code could help implement these changes without requiring complete reproof of theorems.

### Monomial Representations in Grind

Jay discussed the challenges of implementing monomial representations in Grind, particularly regarding the use of integers versus other number types for proof simplification. He proposed using exponent vectors to represent monomials as lists of powers, which would eliminate concerns about standardization. The group debated the merits of using vectors versus lists in proofs, with Matthew suggesting that vectors provide useful length proofs for automation but may require rebuilding when serialized. The discussion concluded with agreement that rebuilding length proofs might be acceptable for now, unless specific issues arise later.

### Native Decide Extension Discussion

The team discussed Native Decide, an extension that allows adding new computation types, potentially implemented in C code. Matthew explained that while it provides more granular reporting of assumptions, it doesn't explicitly state "extern" but rather reports lien declarations. Damiano expressed surprise at how granular the reporting had become, initially expecting blanket axioms. The conversation ended mid-discussion about previous implementation phases of Native Decide.

### Side-Firing Implementation in Lean Discussion

The team discussed the implementation of side-firing in Lean, with Damiano confirming that while it produces a blanket result, inspecting the term reveals the specific components used. Jay raised questions about Native Decide's trust in the compiler, to which Matthew explained that it relies on the axiom of reduced Boole and can verify the lean terms being used. The discussion also touched on GMP implementation in the kernel, with Matthew noting that while it's enabled by default on some architectures, it can be turned off locally with appropriate flags.

### Quotient Types in Lean Discussion

The group discussed the use of quotient types and their effectiveness in Lean, particularly regarding polynomial representations and handling order independence. Damiano explained that while quotient types are mathematically convenient, they introduce additional axioms that can create computational friction. Matthew noted that quotient types often lead to inefficient proofs and can anger type theorists due to lack of computational data. The discussion concluded with Damiano suggesting they should identify the atomic operations that Macaulay 2 performs on polynomials to potentially align their representation in Lean with Macaulay's approach.

### Math Software Verification Approaches

The group discussed verification approaches for mathematical software, particularly focusing on Macaulay 2 and Rust code. Matthew shared insights about a recent post by Leo regarding verifying C libraries in Signal using AI-assisted verification through translation to Lean. The discussion explored the potential for using AI to verify core components of mathematical software, though concerns were raised about stack overflow issues and the complexity of translating optimized code. The conversation concluded with questions about Lean's multi-core programming capabilities for handling intensive computational tasks.

### Algorithm Verification in Lean Discussion

The group discussed implementing and verifying algorithms, particularly focusing on the challenges of using Lean for verifying Rust implementations involving asynchronous programming and complex control flow. Damiano explained that formalizing imperative code with features like early exits and I/O operations presents significant complexity challenges in Lean. The discussion then shifted to exploring whether Macaulay 2's operations could be traced and potentially mirrored in Lean for verification purposes, with Michael noting that while Macaulay 2 doesn't currently keep operation traces, it could be implemented. Anton suggested starting with a simpler approach of implementing standalone polynomial arithmetic in Rust that could be verified by Lean as a proof of concept.

### Polynomial Multiplication Implementation Challenges

The team discussed challenges with implementing polynomial multiplication in Lean, particularly around kernel performance issues and expression size. Jay explained that while basic polynomial multiplication can be implemented in Lean, the main bottleneck comes from the kernel's difficulty handling large expressions, which can cause deep recursion errors. The team agreed to focus on developing a new polynomial representation that would be more compact and avoid these large expressions, with Jay noting that previous work on this was about 80% complete but required additional serialization and deserialization components. Douglas agreed to review an old Merdy package update branch, while the team confirmed that improved error messages would be included in the upcoming release.
